STEP 1
यह आप करें

Accounts (जो पहले से हों उन्हें छोड़ दीजिए)

  1. GitHub (github.com): जहाँ आपका कोड निजी तौर पर रहता है। Account business email से बनाइए, two-factor authentication चालू कीजिए।
  2. Supabase (supabase.com): आपका database। अपने GitHub account से sign in कीजिए (एक बटन, कोई नया password नहीं)।
  3. Vercel (vercel.com): आपके ऐप को online रखता है। यह भी GitHub से sign in कीजिए।
  4. Claude Code: claude.com/claude-code पर दिए निर्देशों से अपने computer पर install कीजिए और अपने Claude account से sign in कीजिए। यही वह account है जो आपका सिस्टम बनाता है और बाद में चलाता है, जिसका खर्च आप उठाते हैं।
  5. Node.js और Git: दो मुफ़्त tools जो Claude Code को आपकी मशीन पर चाहिए। nodejs.org से Node.js LTS और git-scm.com से Git install कीजिए, defaults स्वीकार करते हुए। यहाँ कुछ गड़बड़ हो तो Step 3 पूरा करके Claude से ठीक करवा लीजिए: वह जाँच कर मरम्मत खुद कर सकता है।
STEP 2
यह आप करें

Database project और उसकी तीन keys

  1. Supabase में: New project। नाम अपने business पर रखिए। Region: आपके सबसे पास वाला (भारत के लिए Mumbai)। एक मज़बूत database password बनने दीजिए और उसे सुरक्षित जगह save कर लीजिए।
  2. Project Settings → API खोलिए और यह page खुला रखिए। यहाँ तीन values दिखेंगी: Project URL, anon key, और service_role key। Step 4 में जब Claude माँगेगा तब आप इन्हें paste करेंगे। service_role key को bank के password की तरह समझिए: किसी को message मत कीजिए, और ऐसी किसी file में मत रखिए जो Claude commit करे।
STEP 3
यह आप करें

Folder और session

  1. इस build के लिए एक folder बनाइए, अपने business के नाम पर, जैसे Documents\mybusiness-os। ज़िंदगी भर सब कुछ यहीं रहेगा: यह पहला सिस्टम और इसके बाद का हर सिस्टम।
  2. अपने AI Systems Blueprint (.md या .pdf) की एक copy उस folder में रखिए।
  3. उस folder में terminal खोलकर Claude Code शुरू कीजिए। आज से हर बैठक ठीक ऐसे ही शुरू होगी: folder खोलिए, Claude Code शुरू कीजिए।
STEP 4
Claude Code में पेस्ट करें

दिन 1 का prompt: यह पूरा block अपने पहले message की तरह paste कीजिए।

Paste · Message 1

आप मेरा business platform शून्य से set कर रहे हैं। मेरा AI Systems Blueprint इसी folder में है; उसे पढ़िए ताकि आप मेरा business समझ लें। फिर नीचे के काम एक-एक करके कीजिए, हर step के बाद सरल शब्दों में बताइए कि आपने क्या किया, और जहाँ भी कोई चीज़ सिर्फ़ मेरे पास है वहाँ रुककर मुझसे माँगिए।

  1. जाँचिए कि Node.js और Git installed हैं और चल रहे हैं। कुछ missing या ख़राब हो तो मुझे ठीक-ठीक बताइए कि क्या download करना है और कहाँ click करना है, फिर दोबारा जाँचिए।
  2. इसी folder में TypeScript के साथ एक Next.js ऐप बनाइए, standard defaults स्वीकार करते हुए। पक्का कीजिए कि वह मेरी मशीन पर चलता है और मुझे खोलने का local address दिखाइए।
  3. इस folder में Git set कीजिए और पहला commit कीजिए।
  4. मेरे GitHub account पर इस folder के नाम की एक PRIVATE repository बनाने में मेरी मदद कीजिए, और कोड उसमें push कीजिए। Browser में login का कोई भी step मुझे साथ-साथ करा दीजिए। Repository private ही होनी चाहिए।
  5. मेरी secret keys के लिए .env.local नाम की file बनाइए और पक्का कीजिए कि Git उसे ignore करे। फिर मुझसे तीन values एक-एक करके माँगिए: मेरा Supabase Project URL, मेरी anon key, और मेरी service_role key। उन्हें file में आप ख़ुद डालिए। Keys मुझे chat में कभी दोहराकर मत दिखाइए, किसी और file में मत लिखिए, और कभी commit मत कीजिए।
  6. इस project के लिए एक CLAUDE.md file बनाइए। घर के नियम मैं अगले message में paste करूँगा; उनका इंतज़ार कीजिए।
  7. यह सब हो जाए तो मुझे बताइए कि project Vercel के लिए तैयार है और याद दिलाइए कि मैं guide के Step 5 पर लौटूँ।

फिर अपने दूसरे message में Part 03 के छह घर के नियम ठीक वैसे ही paste कीजिए जैसे वहाँ लिखे हैं, और Claude से कहिए: “इन्हें CLAUDE.md में स्थायी नियमों की तरह रखो, इस folder में तुम जो भी कभी बनाओ उन सब के लिए।”

STEP 5
यह आप करें

उसे online कीजिए

  1. Vercel में: Add New → Project → Import कीजिए, वही repository जो अभी push की। Vercel ऐप को अपने आप पहचान लेता है।
  2. Deploy से पहले Step 2 वाली तीनों values Environment Variables की तरह डालिए (नाम ठीक क्या रखने हैं, Claude से पूछिए: “मेरी .env.local में environment variable के क्या नाम हैं?”)।
  3. Deploy दबाइए। करीब दो मिनट बाद आपका ऐप .vercel.app पर ख़त्म होने वाले address पर live है।
  4. वह address अपने phone पर खोलिए और home screen पर add कर लीजिए। आज से, जब भी Claude commit करके push करेगा, live ऐप अपने आप update हो जाएगा। Publish करने का पूरा सिस्टम बस यही है; कोई और step नहीं, कभी नहीं।
दिन 1 पूरा तब है जब: ऐप अपने live address पर आपके phone पर खुलता है; GitHub पर repository private है; आपकी तीनों keys सिर्फ़ .env.local में और Vercel की settings में हैं; और CLAUDE.md में छह घर के नियम हैं। इनमें से कुछ भी सही न हो तो वही बात Claude Code में paste कीजिए और आगे बढ़ने से पहले ठीक करवाइए।

दिन 1 के बाद हर बैठक
पाँच आदतें
  1. पहले plan। हर काम की शुरुआत इससे कीजिए: “पहले plan बनाओ और किसी file को छूने से पहले मेरी हाँ का इंतज़ार करो।” Plan पढ़िए। कोई पंक्ति समझ न आए तो सरल शब्द माँगिए। तभी आगे बढ़ने को कहिए।
  2. हर बैठक में एक छोटी, पूरी चीज़। ऐसा एक घंटा जो एक चलती हुई screen पर ख़त्म हो, उन तीन घंटों से बेहतर है जो छह अधूरी चीज़ों पर ख़त्म हों।
  3. काम save कीजिए। कोई चीज़ चल जाए तो कहिए: “Commit and push.” इससे आपका काम भी save होता है और live ऐप भी update हो जाता है। हर बैठक में कम से कम एक बार।
  4. कुछ टूटे तो error paste कीजिए। कहिए: “इसे सरल शब्दों में समझाओ और ठीक करो।” अटकना बनाने का सामान्य हिस्सा है, और यही वह tool है जो आधी रात को भी जवाब देता है।
  5. बैठक बंद कीजिए। पूछिए: “आज हमने क्या किया और आगे क्या है, संक्षेप में बताओ और एक notes file में save करो।” अगली बैठक उसी note को पढ़कर शुरू होगी। Note और अपने सवाल Sunday live class में लेकर आइए।

1.2
उसे एक SLICE तक काटिए
पाँच कट, क्रम से

पहला build जीतने वाले सिस्टम का वह सबसे छोटा टुकड़ा है जो बताया गया दर्द हटा दे:

SLICE का नियम: एक flow, एक trigger, एक नतीजा, एक user समूह। आपको एक वाक्य में कहना आना चाहिए: “जब X होता है, सिस्टम Y करता है, और Z उसे देखता है।” एक वाक्य। न समाए तो और काटिए।

जो भी कटे वह “बाद में” की सूची में जाता है और अगले build की तरह लौटता है:

  1. Channels: सबसे ज़्यादा volume वाला एक channel रखिए; बाक़ी बाद में।
  2. लोग: वे एक-दो लोग रखिए जो रोज़ दर्द झेलते हैं; portals और बाक़ी सबकी screens बाद में।
  3. दस्तावेज़: वह एक दस्तावेज़ रखिए जो सबसे ज़्यादा हाथ से बनता है; बाक़ी सारे format बाद में।
  4. Automation: Blueprint जितनी इजाज़त दे उससे एक स्तर नीचे बनाइए: भेज सकता हो तो draft तक बनाइए; draft कर सकता हो तो सिर्फ़ record तक। Auto सिर्फ़ Part 04 में चालू होता है।
  5. Connections: आपके मौजूदा software से एक बार का export; कोई live link नहीं, और आपके billing या accounting सिस्टम में लिखना कभी नहीं।

किसी भी आकार पर ये कभी न काटें: Blueprint के §4 के guardrails, हर अनिश्चित चीज़ के लिए “needs review” का रास्ता, सिस्टम ने क्या किया उसकी डायरी, और एक switch जो किसी भी automatic व्यवहार को बंद कर दे।

नियम 1 · एक घर

यह folder, यह repository, यह database और यह ऐप ही इस business के इकलौते होंगे, हमेशा। हर नया सिस्टम उसी घर का एक नया कमरा है: ऐप का एक नया हिस्सा जो वही ग्राहक सूची, वही orders, वही logins पढ़ता है। किसी नए सिस्टम के लिए दूसरा ऐप, दूसरा database या दूसरी repository कभी मत बनाओ।

क्यों: जिस business के आठ सिस्टम आठ ऐप्स में हों, उसके आठ logins और ग्राहक सूची की आठ copies होती हैं, और वह एक screen जो सब कुछ दिखाए, कभी बन ही नहीं पाती।

नियम 2 · हर इंसान की अपनी चाबी

टीम के हर सदस्य का अपना login। हर इंसान को ठीक उतना दिखे जितना उसके काम को चाहिए, उससे ज़्यादा कुछ नहीं; owner को सब दिखे। साझा password कभी नहीं।

क्यों: “किसने क्या किया” का मतलब तभी है जब हर कोई ख़ुद अपने नाम से हो।

नियम 3 · ग्राहक तक कुछ भी पहुँचे, उससे पहले इंसान की हाँ

कोई चीज़ ग्राहक को नहीं भेजी जाती, और कोई दाम, discount, credit या वादा नहीं दिया जाता, जब तक कोई नामज़द इंसान पहले approve न करे। Automatic भेजना सिर्फ़ उन message-प्रकारों के लिए है जिन्हें owner ने test के बाद जानबूझकर चालू किया हो, और एक ऐसा switch हमेशा रहे जो बिना कोड छुए सारा automatic व्यवहार बंद कर दे।

क्यों: भरोसा एक ग़लत message में ख़र्च हो जाता है और महीनों में वापस कमाया जाता है।

नियम 4 · वह डायरी जिसे कोई बदल न सके

सिस्टम जो भी करे (हर message, हर बदलाव, हर approval, हर ग़लती) वह एक ऐसे log में लिखा जाए जो कभी edit या delete न हो सके, सिर्फ़ आगे बढ़े।

क्यों: समीक्षा उस पर चलती है जो सचमुच हुआ, उस पर नहीं जो किसी को याद है।

नियम 5 · SECRETS अलमारी में रहें

Keys और passwords सिर्फ़ इस मशीन की .env.local में और online hosting की settings में रहें। वे कोड में, chat में, या GitHub जाने वाली किसी file में कभी न दिखें।

क्यों: कोड में रखी key उस हर इंसान को दी हुई key है जो कभी वह कोड देखेगा।

नियम 6 · पैसा हिसाब से निकले, अंदाज़े से कभी नहीं

दाम, मात्रा, जोड़ और stock के आँकड़े owner के अपने आँकड़ों से बने पक्के नियमों के कोड से आएँ, और वे नियम असली पुराने उदाहरणों पर test हों। AI पढ़ता है, मिलाता है, draft करता है, याद दिलाता है; कोई संख्या वह कभी नहीं गढ़ता।

क्यों: दाम का अंदाज़ा लगाने वाला AI पूरे आत्मविश्वास से ग़लत होता है। हिसाब या तो सही होता है या टूटा हुआ साफ़ दिखता है।

नियमों को ईमानदार रखना: Claude कभी कुछ ऐसा सुझाए जो इनमें से किसी नियम को मोड़ता हो, तो उसे खुलकर कहना होगा और रुकना होगा। और आपको कभी शक हो कि नियम अब भी माने जा रहे हैं या नहीं, तो paste कीजिए: “इस project की CLAUDE.md के छह घर के नियमों पर जाँच करो और जो भी टूटता हो, सरल शब्दों में बताओ।”
Part 04टेस्ट, भरोसा, फिर चालू
पाँच मामले, एक हफ़्ता, एक switch

पूरा business किसी नए सिस्टम पर एक दिन में कभी नहीं पलटा जाता। पहले आप अपना भरोसा कमाते हैं, फिर टीम का, फिर ग्राहकों का। यह हिस्सा वही चार चालें हैं, आपके हर आने वाले सिस्टम के लिए एक जैसी।

4.1
पाँच असली मामले, बटन पर आपका अँगूठा
अभी कुछ भी automatic नहीं

पाँच असली, चालू मामले चुनिए: ऐसे ग्राहक जिन्हें आप इतना जानते हों कि कुछ ग़लत पहुँचे तो ख़ुद phone कर सकें, जिनमें आपकी भाषाएँ और आम तरह के orders आ जाएँ। हर एक को सिस्टम से गुज़ारिए। सिस्टम draft करे; हर बटन आप दबाइए। हर ग़लत शब्द, ग़लत आँकड़ा, ग़लत समय अपने “जो नियम सीखे” note में लिखिए, और हर एक Claude से ठीक करवाइए।

4.2
निगरानी का हफ़्ता

पूरे एक हफ़्ते सिस्टम अपने दायरे का सब कुछ draft करे, और आपकी टीम उसके बग़ल में पुराने ढंग से काम करती रहे। हर दिन मिलाइए: सिस्टम ने क्या तैयार किया, और आपके लोगों ने सचमुच क्या भेजा या किया? हर फ़र्क़ या तो सिस्टम की मरम्मत है या आपकी Build Sheet से छूटा हुआ नियम। पुराना तरीक़ा बंद नहीं होता; अभी कुछ भी बंद नहीं होता।

Done when: एक ऐसा हफ़्ता निकल जाए जिसमें सिस्टम के draft और हक़ीक़त मिलते हों, और हर अपवाद कहीं पहुँचने से पहले “needs review” के रास्ते पकड़ा गया हो।

Automatic व्यवहार सिर्फ़ उसके लिए चालू कीजिए जो निगरानी के हफ़्ते से पास हुआ, और सिर्फ़ वही जो आपके Blueprint की “AI अकेले कर सकता है” सूची में है: reminders, status updates, अंदरूनी सूचनाएँ। Sign-off सूची की हर चीज़ हमेशा इंसान के पास रहती है। Automation को business WhatsApp number चाहिए तो यही वह हफ़्ता है जब वह घड़ी (Part 01) काम आती है। पाँच मामलों से बढ़कर एक route, एक विभाग या ग्राहकों के एक समूह तक जाइए, सब पर एक साथ कभी नहीं। एक भी ग़लत message जाए: switch से बंद कीजिए, ठीक कीजिए, पाँच पर दोबारा test कीजिए, फिर चालू कीजिए।

4.4
टीम, और समीक्षा
अपनाया जाना ही असली finish line है
  • पहले एक इंसान। सिस्टम उस एक सदस्य को दीजिए जो पुराना दर्द सबसे ज़्यादा झेलता है; उसकी राहत बाक़ियों को खींच लाएगी। पूरी टीम पर एलान करके कभी launch मत कीजिए।
  • सिस्टम लोगों को काम थमाता है; उन पर नज़र नहीं रखता। हर screen “अब मुझे क्या करना है” का जवाब दे, “कौन धीमा था” का नहीं। Reports सिस्टम में हुए काम की उपज हों, कोई form नहीं जिसे कोई भरे।
  • Owner की समीक्षा डायरी से चले। Switch वाले हफ़्ते के अंत में यादें नहीं, log पढ़िए: क्या अपने आप चला, क्या flag हुआ, क्या सुधरा। Guardrails adjust कीजिए, Claude से बदलाव commit करवाइए, और उन्हें lock कर दीजिए।
4.5
सिस्टम दो
उसी घर में एक नया कमरा

उसी Blueprint के साथ वापस Part 01 पर: आपके First Build Card की “बाद में” सूची ही menu है, और आपका पहला सिस्टम जो data लिखता आ रहा है वही आगे की बढ़त। वही folder, वही ऐप, वही database, वही छह नियम: उसी घर में एक नया कमरा। हर build पिछले से तेज़ होता है, क्योंकि घर पहले से खड़ा है।

हर महीने का खड़ा इम्तिहान: phone पर live ऐप खोलिए और तीन सवाल पूछिए। क्या सूची अब भी सच्ची है? क्या कोई चीज़ बिना ज़रूरी हाँ के ग्राहक तक पहुँची? क्या डायरी आपका हफ़्ता आपकी याददाश्त से बेहतर समझाती है? तीन हाँ: अगला कमरा बनाइए। कोई भी ना: कुछ भी नया करने से पहले उसे ठीक कीजिए।
